建议时长：40-45 分钟
课堂主线：导入不超过 2 分钟，其余时间以学生自主探究活动页任务为主，教师只做任务发布、巡视点拨和关键收束。
学生入口：http://159.75.213.93/system-builder/openclass
活动页：http://159.75.213.93/activity-submit/activity

## 0. 课前准备

教师提前打开：

1. 活动页，停在“情境导入”。
2. 学生半成品画布，确认能进入 `openclass`。
3. 教师后台，确认能看到学生每个环节的提交进度，课堂中不投登录页。
4. 导学案或纸笔，提醒学生必要时先记录证据，再回活动页提交。

课堂组织原则：

- 教师导入只负责明确问题、任务和证据线，不展开讲解，控制在 2 分钟内。
- 每个环节先让学生独立或同桌探究，教师巡视时用问题点拨，不直接报答案。
- 全班收束只抓关键分歧和容易错的证据，时间控制在 1-2 分钟。
- 每个答案都追问证据来源：情境、画布、代码、日志、数据库或网页。
- micro:bit 和扩展板合称“智能终端”；IoT 模块负责联网，不和智能终端混成一个设备。

板书预留：

```text
信息系统 = 人 + 硬件 + 软件 + 网络 + 数据

今天的证据线：
需求 -> 画布连接 -> 代码语句 -> 运行现象 -> 故障原因
```

## 一、情境导入：2 分钟快速入题

教师投活动页“情境导入”。

教师：

> 这节课不是老师带着大家一句一句填答案。你们要根据活动页和画布自己完成四个任务：硬件搭建、软件分析、运行排错、自我评价。每填一个答案，都要能说出证据在哪里。

教师指向活动页情境文字：

> 现在给大家 30 秒，只看情境，圈出这个系统至少要完成的事情。不要急着操作。

学生默读 30 秒。

教师快速收束：

> 好，今天我们抓四件事：感知温度、异常提醒、远程查看、保存记录。传感器、蜂鸣器、智能终端、IoT 模块、服务器、数据库和浏览器，都会围绕这四件事出现。下面直接进入第一个任务，自己从画布里找证据。

板书：

```text
感知温度 / 异常提醒 / 远程查看 / 保存记录
```

过渡：

## 二、硬件搭建：学生自主观察画布（约 8 分钟）

教师投学生半成品画布，让学生打开活动页“硬件搭建”。

教师发布任务：

> 这个环节给大家 5 分钟自主完成。任务有三步：第一，判断还缺哪两个设备；第二，在画布中补上它们；第三，观察关键线接到智能终端哪个引脚，并完成活动页“硬件搭建”的记录。

教师强调：

> 先不要问同学答案，也不要急着提交。你要能说清楚：我为什么选这个设备，它的线接在哪里。

学生自主操作 4-5 分钟。教师巡视，只用短问题点拨：

> 你选的这个设备负责“感知”还是“动作”？
> 传感器看 DATA 线，蜂鸣器看 IO 线。
> 你现在看的线是数据线，还是电源线？
> 你这个答案能在画布上指给我看吗？

如果有学生卡住，教师不直接给答案：

> 回到情境，“温度变化”需要谁感知？“声音提醒”需要谁执行？你先按功能找设备。

全班 1 分钟收束。

教师：

> 停一下，只核对两个关键证据。温湿度传感器的 DATA 接到哪个引脚？

预期学生：P1。

教师：

> 蜂鸣器的 IO 接到哪个引脚？

预期学生：P2。

教师板书：

```text
画布证据：
传感器 DATA -> P1
蜂鸣器 IO -> P2
```

教师：

> 这两个结论后面读代码、排错都会用。现在继续完成“模块功能匹配”，还是先自己判断，不会的同桌互相说明理由。

学生继续完成模块功能匹配 2 分钟。

教师巡视追问：

> “读取温度”是传感器自己读，还是智能终端程序读？
> “发送 HTTP 请求”主要依赖哪个联网模块？
> “接收上传、保存数据、提供网页”是哪个服务端模块做的？

教师简短收束：

> 传感器是数据来源，智能终端负责读取和判断，IoT 模块负责联网发送，Flask 服务器接收和提供网页，数据库保存记录，浏览器或手机是人查看数据的入口。

教师：

> 现在提交“硬件观察”。提交以后进入软件分析，用代码验证刚才的画布证据。

过渡：

> 第二个任务的重点不是听老师翻译代码，而是你自己从代码里找四类证据。

## 三、软件分析：学生读代码找证据（约 14 分钟）

教师投活动页“软件分析”。

教师发布任务：

> 软件分析给大家 7 分钟先自主完成。请你在代码里找四类证据：网络参数、上传地址、读取传感器的引脚、控制蜂鸣器的引脚。找到了再填活动页，不确定的先和同桌核对。

教师给读代码方法，不展开讲解：

> 看代码时不用每一行都懂。先抓变量名、路由名和 pin 编号。凡是 `SERVER`、`UPLOAD_ROUTE`、`read_analog`、`write_digital`，都要重点看。

学生自主阅读与填写 5-7 分钟。教师巡视点拨：

> `SERVER_IP` 和 `SERVER_PORT` 对应画布里的谁？
> `/upload` 是上传数据，还是浏览器查看？
> `pin1.read_analog()` 对应画布哪个 P 引脚？
> `pin2.write_digital()` 是读取数据，还是控制执行器？
> 你写的 URL 里有没有协议、IP、端口、路由和参数？

同桌核对 1 分钟。

教师：

> 和同桌互查三件事：第一，上传 URL 有没有写完整；第二，读取引脚和画布是否一致；第三，上传地址和浏览器查看地址有没有混在一起。

全班关键收束，控制在 3 分钟。

教师指向智能终端代码：

```python
SERVER_IP = "192.168.1.100"
SERVER_PORT = 5000
UPLOAD_ROUTE = "/upload"
```

教师：

> 这三项决定服务器位置和上传入口。上传地址不是只写 IP，要有 IP、端口、路由。

教师指向上传语句：

```python
url = "http://" + SERVER_IP + ":" + str(SERVER_PORT) + UPLOAD_ROUTE
url = url + "?id=1&val=" + str(temp)
obloq.http_get(url)
```

教师：

> 如果温度是 32.5，上传地址大概是 `http://192.168.1.100:5000/upload?id=1&val=32.5`。注意，这是智能终端上传数据用的，不是浏览器查看页面用的。

教师指向引脚语句：

```python
raw = pin1.read_analog()
pin2.write_digital(1)
pin2.write_digital(0)
```

教师：

> 画布里传感器 DATA 接 P1，代码里 `pin1.read_analog()` 读 P1；画布里蜂鸣器 IO 接 P2，代码里 `pin2.write_digital()` 控制 P2。这里画布和代码是对应的。

教师指向 Flask 路由：

```python
@app.route('/upload', methods=['GET'])
def upload_data():
```

教师：

> `/upload` 是智能终端上传温度数据的入口，问号后面带 `id` 和 `val`。服务器接收后会判断阈值、写入数据库，并返回控制结果。

教师指向首页路由：

```python
@app.route('/', methods=['GET'])
def index():
```

教师：

> `/` 是浏览器或手机查看页面的入口。如果服务器 IP 是 `192.168.1.100`，端口是 `5000`，浏览器查看地址就是 `http://192.168.1.100:5000/`。

教师提醒：

> 现在提交“软件分析”。提交前检查一遍：你写的是上传地址，还是查看地址？不要混。

过渡：

> 前两个任务你们已经找到了画布证据和代码证据。第三个任务要靠运行现象判断问题，不是靠猜。

## 四、运行排错：学生按现象选择排错路径（约 13-14 分钟）

教师切到学生画布或运行页面。

教师发布任务：

> 运行排错这个环节先给大家 6 分钟自己做。运行系统，观察三处：日志有没有上传请求，数据库或页面有没有记录，温度超过阈值时蜂鸣器有没有响应。然后在活动页填写排错记录和可能原因。

教师强调：

> 不要求大家一开始就完全正确，但必须按现象判断。不要一句“服务器坏了”或者“传感器坏了”就结束。

学生自主运行与填写。教师巡视点拨：

> 你现在看到的现象是什么？先描述现象，再说原因。
> 数据库有记录吗？如果有，前面的采集和上传是不是至少通了一部分？
> 蜂鸣器不响时，你先查控制引脚，还是先查浏览器？
> 页面看不到数据时，你写的是首页地址，还是上传地址？
> 你选的故障原因能不能和现象对应上？

同桌讨论 1 分钟。

教师：

> 同桌互相问一句：你选这个故障原因的证据是什么？说不出证据的，回到画布、代码或日志再看。

全班收束，只讲三条路径。

教师：

> 如果完全没有数据，先查数据从哪里开始产生。

板书：

```text
没有数据：
传感器 DATA -> 读取引脚 -> IoT/WiFi -> /upload -> 数据库
```

教师：

> 如果数据库有数据但蜂鸣器不响，说明采集、上传、保存至少走通了，问题更靠近控制执行器。

板书：

```text
有数据但不报警：
阈值判断 -> 控制引脚 -> 蜂鸣器 IO -> 执行器
```

教师：

> 如果蜂鸣器有反应但网页看不到，说明温度读到了，也做了阈值判断，问题更可能在浏览器地址、首页路由、数据库查询或页面显示。

板书：

```text
数据有但页面不显示：
浏览器 URL -> Flask 首页 / -> 数据库查询 -> 页面渲染
```

教师：

> 现在提交“运行排错”。提交后看最后一个环节，自我评价要根据自己刚才的完成情况来打分。

过渡：

> 最后一环不是老师总结给你听，而是你判断自己哪些能力已经能独立完成。

教师打开教师后台短暂展示提交进度：

> 我这里能看到每个同学每个环节的提交情况。没有提交的同学先补当前环节；已经提交的同学检查自己的答案有没有证据支撑。

收束 1 分钟：

> 今天我们用一个存储间温度监测问题复习信息系统。你们不是听老师讲完，而是自己完成了四个活动：从需求选硬件，从画布找引脚，从代码找上传和查看地址，从运行现象判断故障位置。以后遇到信息系统题，就按这条线想：数据从哪里来，谁处理，怎么传，存到哪里，谁查看，哪里可能出错。

最后板书：

```text
数据流：
温度 -> 智能终端 -> IoT/WiFi -> Flask /upload -> 数据库 -> Flask / -> 浏览器/手机

排错原则：
先看证据，再推原因；先定位环节，再改参数。
```

## 六、课堂中常见情况与现场话术

学生一开始等老师讲、不动手：

> 这节课不是老师先讲答案。你先根据活动页完成一个判断，哪怕不确定，也要先写出你的证据。

学生问“老师直接告诉我选什么设备”：

> 先回到情境。要“感知温度变化”找哪类设备？要“发出声音提醒”找哪类设备？你先按功能选。

学生把温湿度传感器和蜂鸣器都只说成“硬件”：

> 都是硬件没错，但作用不同。一个负责感知，一个负责执行。信息系统题常考“谁负责什么”，不能只停在“它是硬件”。

学生问“老师直接告诉我 URL 吧”：

> 你先自己找三个东西：服务器 IP、端口、路由。再判断这是上传数据，还是浏览器查看数据。找完我帮你看是否完整。

学生把上传 URL 和浏览器查看 URL 混用：

> 先问一句：这个地址是给谁用的？智能终端上传温度，要写 `/upload?id=...&val=...`；人用浏览器看页面，访问首页 `/`。

学生看到 `pin1` 不知道对应 P1：

> micro:bit 代码里的 `pin1` 对应画布上的 P1，`pin2` 对应 P2。今天重点是把代码和画布对应起来。

学生说“数据库有数据但网页没有，所以传感器坏了”：

> 数据库已经有数据，说明传感器到服务器保存这条路至少走通了一部分。现在问题更可能在浏览器 URL、首页路由、查询或页面显示。

学生说“蜂鸣器不响，所以 Flask 坏了”：

> 先看有没有温度记录。如果数据已经上传并保存了，问题范围就往控制引脚、蜂鸣器连线或执行器本身收缩。

学生自评全打 5 分：

> 可以打 5，但要经得住换题。换成 `pin0.read_analog()`、`pin8.write_digital()`，你还能判断读取引脚和控制引脚吗？能，就打 5；不能，就诚实打 3 或 4。

时间不够时：

> 优先保三件事：画布引脚和代码引脚对应、上传 URL 和查看 URL 区分、根据现象选择排错路径。模块功能匹配和拓展思考可以课后用导学案补。
